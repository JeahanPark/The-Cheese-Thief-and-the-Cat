스팀 매칭 — 수명과 접속

첫 2인 실기기 테스트에서 잡은 구조 결함과 수정 4건. 핵심 원칙은 하나다 — 스팀 클라이언트의 수명은 SteamBootstrap 혼자 소유한다. 세션이 끝나는 것과 스팀이 꺼지는 것은 다른 일이다.

무엇이 터졌나

증상 (실기기 로그)판정
상대 화면 Lobby.GetData NRE 매 프레임 폭주 세션 종료가 스팀을 통째로 죽인 뒤, 로비 UI가 죽은 스팀을 OnGUI마다 찔렀다
종료 시 Lobby.Leave NRE 같은 뿌리 — NGO가 앱 종료 처리에서 스팀을 먼저 내렸다
양방향 모두 접속 불성립 (인원 2가 없다) 식은 릴레이 위에서 ConnectRelay가 10초 타임아웃과 경주 — 유력 원인, 재테스트로 확정
클라 [SteamLobby] 참여: … + 긴 스택 에러 아님 — 개발 빌드는 모든 로그에 스택을 붙인다

원인 — 사라진 호출 하나

트랜스포트(Facepunch)의 Shutdown()이 SteamClient.Shutdown()까지 불렀다. NGO는 Disconnect 버튼·접속 실패 정리·앱 종료 때마다 transport.Shutdown()을 부르므로, 세션 한 번에 스팀 전체가 내려갔다.

수정 4건

#수정효과
1트랜스포트에서 SteamClient.Shutdown() 제거 세션이 끝나도 스팀은 산다 — 방 목록·재호스트·NRE 폭주 해소
2SteamBootstrap init 직후 릴레이 예열 기존엔 ConnectRelay가 식은 릴레이 위에서 10초와 경주 — 접속 불성립의 유력 원인
3첫 접속 타임아웃 10초 → 25초 NAT·릴레이가 느린 환경 여유
4접속 이벤트 로그 Developer → Normal 테스터 화면 콘솔(` 키)에서 접속 단계가 보인다

다음 2인 테스트에서 볼 것 — Connecting with …만 뜨고 Connected with …가 안 뜨면 네트워크(NAT) 문제로 확정, 둘 다 뜨면 해결이다. 새 빌드(Builds/Windows-Dev 폴더째)를 양쪽 다 써야 한다 — 이전 빌드엔 수정이 없다.

종료 순서 함정 — 앱 종료 시 NGO의 OnApplicationQuit(→ transport.Shutdown)이 Application.quitting 구독자보다 먼저 돈다. 로비 이탈은 quitting에서 하되 Ready 가드 + try/catch로 감싼다. 프로세스가 죽으면 스팀이 알아서 방에서 빼 주므로 유령 방은 안 남는다.
