# 쥐·고양이 눈 — 얹은 구를 걷어내고 팩 메시의 셰이프키로 간다

**날짜**: 2026-09-13
**상태**: **완료** — A/B 검수에서 셰이프키(A)가 선택됐고 구 경로는 지웠다(2026-09-13)

## 1. 전제가 틀렸다

`EyeLook`이 흰자·눈동자·눈꺼풀 **구 3개를 런타임에 만들어 머리 본에 얹는** 이유는
클래스 주석에 이렇게 적혀 있다:

> 팩 모델(Quirky Pets)의 눈은 본도 아니고 텍스처도 아니다. 8×8 팔레트를 UV로 찍은
> **스킨드 메시의 한 덩어리**라 돌릴 트랜스폼이 없다(2026-09-08 실측).

「돌릴 트랜스폼이 없다」는 맞다. 하지만 **「눈동자를 못 움직인다」는 틀렸다.**
블렌더로 `Mouse_LOD0.fbx`를 열어 실측했다(2026-09-13):

| 잰 것 | 결과 |
|---|---|
| 셰이프키 개수 | **30개** — `eyes.blink · lookIn · lookOut · lookUp · lookDown · squint · happy · sad · sleep · annoyed · shrink · dead · excited-1/2 · rabid · spin-1/2/3 · cry-1/2 · trauma` + 눈물·땀 8개 |
| LOD 범위 | `Mouse_LOD0~3` · `Cat_LOD0` **전부 30개** — 빠진 것 없음 |
| 유니티 임포트 | `Mouse_LOD0.fbx.meta` 의 `importBlendShapes: 1` — **이미 켜져 있다** |
| 눈동자 이동량 | 각 방향 메시 크기의 **2.2~2.6%** (`lookIn` 2.23% · `lookOut` 2.30% · `lookUp` 2.48% · `lookDown` 2.55%) |
| 2D 섞기 | 5×5 격자가 **거의 완벽한 직사각 격자**로 퍼진다 — 모서리도 안 뭉갠다 |
| 간섭 | 네 방향이 **정확히 같은 98정점**만 건드린다 — 섞어도 서로를 안 지운다 |

**귀는 애초에 우회로가 아니었다.** `EarPerk`는 팩 리그의 진짜 본 `ear.L`·`ear.R`을
`LateUpdate`에서 덧돌린다. 고칠 것이 없다.

### 앞선 렌더 측정이 「lookIn이 안 된다」고 말한 것은 오측이었다

5×5 렌더 격자에서 `lookIn` 최대 열(5/25칸)이 전부 검출 실패로 나왔다. 원인은 셰이프키가
아니라 **카메라**다 — 쥐 눈은 머리 옆면에 있어 동공이 코 쪽으로 완전히 돌면 측면
카메라에서 머리에 가린다. 그림을 버리고 **정점 좌표를 직접 재니** `lookIn`이 `lookOut`과
같은 크기로 움직이는 것이 나왔다. **그림으로 판정하지 않는다**는 이 세션의 반복된 교훈이다.

## 2. 셰이프키가 **못 하는 것** — 이 설계의 핵심 제약

두 눈이 **거울 대칭으로 한 몸처럼** 움직인다. 좌우 49정점씩을 따로 재서 확인했다:

```
eyes.lookIn      왼( -18.5, -39.8,  -1.1)  오른( +18.5, -39.8,  -1.1)
eyes.lookOut     왼( +19.1, +41.1,  -1.1)  오른( -19.1, +41.1,  -1.1)
eyes.lookUp      왼(  +0.6,  +0.6, +44.3)  오른(  -0.6,  +0.6, +44.3)
eyes.lookDown    왼(  +0.1,  +0.8, -45.6)  오른(  -0.1,  +0.8, -45.6)
```

x 성분의 부호가 좌우 반대다. 그래서 표현 가능한 것은:

| | 셰이프키 | 지금 구 |
|---|---|---|
| **모으기/벌리기**(둘 다 코 쪽 ↔ 둘 다 뒤쪽) | ✅ | ✅ |
| **위아래** | ✅ | ✅ |
| **좌우 비대칭**(왼눈은 앞, 오른눈은 뒤 = 옆의 목표를 본다) | ❌ **불가** | ✅ |

**잃는 것은 「옆쪽 목표를 쫓는 비대칭 시선」 하나다.** 이것을 감수할 만한 이유:

- CTC의 조준 방향은 몸 정면과 거의 같다(몸이 조준을 따라 돈다). 머리 로컬에서 본
  시선의 **좌우 성분은 대개 작고 일시적**이다 — 도는 동안의 지연분이다.
- 옆눈 동물은 **한 번에 한 눈만 보인다.** 왼쪽에서 보는 사람에게 `lookIn`은 「왼눈이
  앞을 본다」로 읽히고, 오른쪽에서 보는 사람에게도 똑같이 읽힌다. 대칭이 자연스럽다.
- 이 연출의 값어치인 「저 고양이가 날 봤나」는 **모으기**(가까운 것을 본다)로 읽힌다.

**단정하지 않는다** — 얼굴 인상이 바뀌는 일이라 눈으로 봐야 한다. 그래서 §5의 A/B 검수가
이 설계의 종료 조건이다.

### 눈은 완전히 안 감긴다

29개 키 전부의 동공 덩어리 세로 두께를 쟀다. **0%로 닫는 키가 없다**:

| 키 | 남는 세로 |
|---|---|
| `eyes.blink` | **31%** (가장 많이 닫힘) |
| `eyes.shrink` · `cry-1/2` | 37% |
| `eyes.happy` | 54% |
| `eyes.sleep` · `sad` | 58% |

사용자가 그린 「질끈 감는 쐐기」는 **팩에 없다**(2026-09-12 보류 항목). 이 설계는 그것을
풀지 않는다 — `blink` 31%까지가 한계다. 뒤에 남는 선택지 둘(둘 다 이 설계 밖):
가중치를 1.0 넘게 밀어 외삽하거나(≈146%에서 두께 0이 되는 계산이나 지오메트리가
뒤집힐 수 있어 재 봐야 한다), 블렌더로 새 셰이프키를 저작한다(파이프라인은 이미 있다).

## 3. 정할 것 — 표현 가능한 부분공간으로의 정사영

`EyeLook`은 지금 눈마다 **따로** 시선 방향을 갖는다(`m_GazeR` · `m_GazeL`, 머리 본 로컬).
셰이프키는 대칭 성분만 표현하므로, 두 방향을 **대칭 성분(표현 가능)과 비대칭 성분(불가)**
으로 나누고 대칭 성분만 쓴다. 비대칭 성분을 버리는 것이 곧 §2의 제약이며, 억지로
한쪽 눈에 맞추면 반대쪽 눈이 **틀린 곳**을 보므로 평균이 유일하게 옳은 선택이다.

```
h = (오른눈의 안쪽 편차각 + 왼눈의 안쪽 편차각) / 2 / EyeMaxAngleDeg   ∈ [-1, +1]
v = (오른눈의 위쪽 편차각 + 왼눈의 위쪽 편차각) / 2 / EyeMaxAngleDeg   ∈ [-1, +1]
```

가중치(유니티 0~100):

| 셰이프키 | 가중치 |
|---|---|
| `eyes.lookIn` | `max(0, +h) × 100` |
| `eyes.lookOut` | `max(0, -h) × 100` |
| `eyes.lookUp` | `max(0, +v) × 100` |
| `eyes.lookDown` | `max(0, -v) × 100` |
| `eyes.blink` | `cover × 100` (`cover`는 지금 쓰는 `CurrentCover()` 그대로 — 평상시 깜빡임과 발사 시 감기를 이미 합쳐 준다) |

같은 축의 두 키는 **동시에 0이 아닐 수 없다.** 서로 반대로 밀어 상쇄되는 일이 없다.

## 5-1. 검수 결과 (2026-09-13)

**셰이프키(A)로 정해졌다.** 같은 쥐·같은 카메라·같은 시선(쉬는 상태)으로 찍은 두 장에서 834픽셀이 달라졌고 그 전부가 눈이다 — 구 쪽은 흰자 구의 테두리가 머리에서 떨어져 솟았다.

지운 것: `EyeLook`의 구 생성·`MakePart`·`MakeChild`·`EnsureMeshes`·`BuildSphere`와 `m_UseBlendShapes`/`DevSetEyeMode`/`DevSetVisible`/`DevPupilWorld*`, CSV 다섯 칸(`EyeScleraScale`·`EyePupilRatio`·`EyePupilOffsetRatio`·`EyeFlatten`·`EyeInsetRatio`), `EyeAnchorBaker`의 반경 굽기, `CharmTunerWindow`의 크기 슬라이더 다섯, `TestSetEyeMode`·`TestShowEyes`·`TestHideEyes`.

### 「옆 목표」 손실의 크기 — 인게임 실측 (2026-09-13)

`GazeAim.DevForce`로 봇 쥐의 조준을 몸 기준 **yaw +75도**에 못박고 두 눈의 시선과
렌더러 가중치를 같이 읽었다(쥐 한계: 바깥 30도 · 안쪽 83.5도).

| | 오른눈 | 왼눈 |
|---|---|---|
| 구 방식(실측) | **−29.7도**(바깥) | **+69.0도**(안쪽) |
| 셰이프키 | +19.7도 | +19.7도 |
| 어긋남 | **49.3도** | 49.3도 |

계산이 인게임 가중치를 재현한다(계산 in=66 vs 실측 65) — 숫자를 믿을 수 있다.

**이 각도가 실제로 나오는가**: 사람의 조준은 **카메라 정면**이고 몸은 이동 방향으로
천천히 돈다(`GazeAim.SourceDirection`). 둘은 서로 독립이라 **「달리면서 옆·뒤를 살핀다」**
에서 75도는 예외가 아니라 흔한 값이다 — 숨바꼭질에서 핵심 동작이기도 하다.
봇으로는 이 분포를 못 잰다(봇의 조준은 제 속도 방향이라 몸과 거의 안 벌어진다).

**남은 선택지**(전부 이 설계 밖):
1. 그대로 둔다 — 옆을 살필 때 두 눈이 모이는 것으로 보인다
2. 그 구간만 구를 되살린다 — 두 방식이 공존해 복잡해진다
3. **한쪽 눈만 움직이는 셰이프키를 블렌더로 저작한다**(`lookIn.L`/`lookIn.R`) —
   파이프라인이 이미 있으므로 가능하지만 팩 메시 에셋을 고치는 일이다

## 5. 종료 조건 — A/B를 눈으로 본다

구 방식과 셰이프키 방식을 **같은 거리·같은 각도**로 나란히 찍어 웹 검수 페이지에 올린다
(이 세션에 만든 `Tools/CTC/Dev/클립 검수 페이지 만들기` 계열을 쓴다).

- 임시 스위치는 `[SerializeField] private bool m_UseBlendShapes` + QA 훅 `DevSetEyeMode(bool)`.
  **CSV에 안 내린다** — 밸런스가 아니라 곧 지울 A/B 손잡이다.
- 찍을 것: 정면 · 3/4 · 측면 × (정면 조준 · 위 · 아래 · 옆 목표) × 쥐·고양이.
  **옆 목표 칸이 이 설계의 유일한 후퇴 지점**이므로 반드시 포함한다.
- 사용자가 고른 뒤 **진 쪽을 지운다**(후속 작업). 셰이프키가 이기면 같이 사라지는 것:
  `EyeLook`의 구 생성·`EnsureMeshes`·`MakePart`(≈250줄) · CSV 5칸
  (`EyeScleraScale` · `EyePupilRatio` · `EyePupilOffsetRatio` · `EyeFlatten` · `EyeInsetRatio` ·
  그리고 뜻을 잃는 `EyeInwardPastCenterDeg`) · `EyeAnchorBaker`의 크기 굽기 ·
  `CharmTunerWindow`의 해당 슬라이더.
- **이 설계는 지우는 데까지 가지 않는다.** A/B로 이기는 것을 확인하기 전에 지우면
  되돌릴 길이 없다.

## 6. 테스트

`EyeBlendShapeLogic`은 순수 static이라 EditMode로 전부 덮는다.

| 테스트 | 잡는 것 |
|---|---|
| 정면을 볼 때 네 방향 가중치가 전부 0 | 쉬는 상태에서 눈이 어딘가로 쏠리는 것 |
| 같은 축의 두 키가 동시에 0이 아닌 경우가 없다 | In/Out이 서로 밀어 상쇄되는 것 |
| 안쪽으로 최대각을 볼 때 `lookIn == 100`, `lookOut == 0` | 부호 뒤집힘 |
| 최대각을 **넘겨도** 100을 안 넘는다 | 외삽으로 지오메트리가 터지는 것 |
| 두 눈이 **반대 방향**(비대칭 최대)이면 h가 0에 가깝다 | §2의 제약을 코드가 실제로 그렇게 다루는지 |
| cover 0/0.5/1 → blink 0/50/100 | 감기 배선 |
| 가중치 5개 전부 [0,100] | 유니티에 음수·초과가 들어가는 것 |

**돌연변이 검사**: 가드를 하나 되돌려 빨개지는 것을 확인한다(이 프로젝트의 규율).

플레이모드는 기존 QA 훅 `DevPupilWorldRight()`가 구 전용이라 못 쓴다 — 대신
`EyeBlendShapes`에 `DevWeights()`를 두어 **실제로 렌더러에 들어간 값**을 읽는다.
Model 값만 보면 배선 누락을 못 잡는다(2026-08-09 교훈).

## 7. 안 하는 것 (YAGNI)

- 표정 22개(`happy`·`sad`·`rabid`·`trauma`·눈물·땀) 배선 — **정보 설계 검토를 안 거쳤다.**
  「저 쥐가 지금 어떤 상태인가」를 얼굴로 흘리면 스텔스를 배신할 수 있다(동공 축소를 기각한
  것과 같은 이유). 쓰고 싶으면 그때 따로 기획한다.
- 「질끈 감기」 — §2대로 팩에 없다. 별건이다.
- 고양이 전용 조정 — 같은 셰이프키 이름을 쓰므로 코드가 하나다. 값이 달라야 하면 그때 판다.
- LODGroup 대응 — 지금 프리팹은 `Mouse_LOD0` 하나만 쓴다. 네 LOD 전부에 키가 있으니
  나중에 붙여도 막히지 않는다.
